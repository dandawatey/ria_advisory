Executive Summary
Problem

Finance teams across all i-CFO360 client organisations receive vendor invoices in heterogeneous formats — PDF, Excel, and scanned images. The current manual workflow creates three compounding problems:

  • Speed: 5–15 minutes per invoice of manual ERP data entry
  • Accuracy: 3–8% error rate — industry benchmark for manual keying; errors discovered weeks later during reconciliation
  • Auditability: No trail on who entered what and when; month-end bottleneck with 200–500 invoices queued
Strategic Goal

Build an agentic invoice processing utility within i-CFO360 that: accepts PDF, Excel, and image invoices in batch; uses an AI agent (Claude claude-sonnet-4-6 + tool use) to extract, validate, and resolve ambiguity; surfaces a Finance review console for human approval before any ERP push; and maintains an immutable audit log of every action.

IC-29 8 pts Rohan_Backend_003 Sprint 1
Parsing Engine — PDF / Excel / Image + InvoiceAgent

The parsing engine uses a tiered approach per file type, always falling back to Claude Vision for unstructured or scanned content.

File TypePrimary ParserFallback
PDF (text layer)pdfplumber — text extraction + regex field mappingClaude Vision
PDF (scanned)pdf2image → Claude Vision structured prompt—
Excel (.xlsx/.xls)openpyxl — header detection + column mapping—
Image (JPG/PNG/TIFF)Claude Vision API — structured extraction prompt—

10 mandatory extracted fields: vendor_name, invoice_no, invoice_date, due_date, currency, subtotal, tax_amount, total_amount, line_description, line_amount. Every field carries a confidence score 0–100. Fields < 70 trigger request_human_input via InvoiceAgent.

  • AC-01Text-based PDF with clear layout → all 10 fields extracted, confidence > 85
  • AC-02Scanned PDF → Claude Vision extracts ≥ 8/10 fields; missing fields flagged WARN
  • AC-03Excel invoice → header row detected, line items mapped to canonical fields
  • AC-04Extraction async; upload endpoint returns immediately; frontend polls status
  • AC-05Parsing failure (unreadable file) → status = EXTRACTION_FAILED, error stored
IC-30 5 pts Rohan_Backend_003 Sprint 1
Validation Engine — 7 Rules + State Machine
RuleSeverityCondition
MANDATORY_FIELDSFAILvendor_name, invoice_no, invoice_date, total_amount all present
AMOUNT_CONSISTENCYFAILsubtotal + tax_amount = total_amount (± 0.01 tolerance)
TAX_REASONABLENESSWARNtax_rate between 0–30%; flag if outside range
DATE_VALIDFAILinvoice_date ≤ today; due_date ≥ invoice_date if present
DUPLICATE_INVOICEFAILinvoice_no + vendor_no combination not already POSTED
VENDOR_EXISTSFAILvendor matched to ERP master with confidence ≥ 80%
CURRENCY_SUPPORTEDWARNcurrency code in ERP configured currency list
  • AC-01Invoice with mismatched amounts → FAIL AMOUNT_CONSISTENCY, push blocked
  • AC-02Duplicate invoice # (same vendor, already POSTED) → FAIL DUPLICATE_INVOICE
  • AC-03Unknown vendor → FAIL VENDOR_EXISTS, agent asks Finance to select from candidates
  • AC-04All 7 rules stored in invoice_validations on every extraction
  • AC-05Finance can override WARN with reason; FAIL requires field correction

IC-32 8 pts Rohan_Backend_003 Sprint 2
ERP Push Service — BC + Retry + Idempotency

Phase 1 target: Microsoft Business Central (BC REST API v2.0). Push creates a Purchase Invoice with all line items. Idempotency prevents double-posting.

ScenarioBehaviour
Successful pushstatus = POSTED, erp_document_number stored
Duplicate push (same invoice_id)Return existing ERP doc number — no second BC request
BC auth token expiredPUSH_FAILED status; Finance notified to re-auth
BC API 4xx (data error)PUSH_FAILED; no retry — Finance data issue
BC API 5xx / timeoutRetry up to 3× with exponential backoff (2s, 4s, 8s)
  • AC-01Approved BC invoice → Purchase Invoice created in BC with correct vendor, amount, lines
  • AC-02Duplicate push (same invoice_id) → returns existing ERP doc number
  • AC-03BC 5xx → retries up to 3× with exponential backoff
  • AC-04Push completes within 30 seconds for single invoice under normal conditions
  • AC-05Every push attempt logged in invoice_push_log (append-only)

06
Agentic Architecture — InvoiceAgent
Why Agentic?

A hardcoded pipeline cannot handle the ambiguity inherent in real-world invoices. The AI agent uses reasoning to resolve cases that rule-based parsing fails on:

  • Vendor name on invoice ≠ exact ERP vendor master name (fuzzy matching + Finance confirmation)
  • Scanned invoices with partial OCR failures requiring contextual inference
  • Multi-currency, multi-tax-rate invoices requiring business logic, not just field parsing
  • Agent asks Finance targeted, specific questions — one at a time — instead of a generic "extraction failed" error
Tool Registry (7 Tools)
extract_fields
(file_path, file_type)
Returns InvoiceExtraction with all 10 fields + confidence scores + line items
validate_invoice
(fields)
Runs all 7 validation rules; returns ValidationResult[] with rule, status, message, field_ref
lookup_vendor
(name)
Fuzzy-matches vendor name against ERP master; returns vendor_no, confidence, candidates[]
check_duplicate
(invoice_no, vendor_no)
Checks invoice_no + vendor combination; returns is_duplicate + existing_doc_no if found
request_human_input
(field, question, options[])
PAUSE → surfaces to Review Console → RESUME. Agent loop suspends until Finance answers.
push_to_erp
(invoice, erp_config)
Pushes approved invoice to ERP via ERPInvoicePusher; returns PushResult with doc_no + status
log_audit_event
(event_type, payload)
Writes to invoice_state_log — append-only, immutable
Model: claude-sonnet-4-6
Tool-use loop with human-in-the-loop interrupts. System prompt enforces NEVER push without Finance approval.
Human-in-the-Loop Protocol
Agent calls request_human_input(field="vendor_no",
  question="I found two vendors matching 'Acme'. Which is correct?",
  options=["Acme LLC (V001)", "Acme Corp (V002)", "Neither — enter manually"]
)
  → Backend stores question in invoice_uploads.pending_question (JSONB)
  → Agent loop pauses (returns PENDING token)
  → Frontend Review Console polls GET /api/invoices/{id}
  → On pending_question present → renders question widget
  → Finance selects answer → POST /api/invoices/{id}/answer
  → Backend appends answer to agent conversation history
  → Agent resumes tool loop with confirmed vendor_no

API Design
POST /api/invoices/upload Multipart batch upload (≤50 files, ≤10 MB each) Bearer
GET /api/invoices/{id} Invoice detail: extracted fields + validations + state history Bearer
GET /api/invoices/{id}/file Serve original file (auth-gated — no direct storage URL) Bearer
PATCH /api/invoices/{id}/fields Update extracted field value (Finance correction in review console) Bearer
POST /api/invoices/{id}/answer Submit Finance answer to InvoiceAgent HITL question; resumes agent loop Bearer
POST /api/invoices/{id}/approve Approve invoice for ERP push — requires no FAIL validations Bearer
POST /api/invoices/{id}/reject Reject invoice with reason (min 10 chars) Bearer
POST /api/invoices/{id}/push Push approved invoice to ERP; idempotent on duplicate call Bearer
GET /api/invoices/history Paginated list with status / date / user filters; 25 rows/page Bearer
GET /api/invoices/history/export Streaming CSV export of filtered results (up to 10,000 rows) Bearer
09
Security Requirements
🔐
Authentication
All 10 endpoints require Bearer JWT. No anonymous access. RBAC: finance_user for upload/review, finance_admin for all tenant invoices, admin for full access.
🏢
Multi-Tenant Isolation
Every DB query filters by tenant_id = current_tenant(). Cross-tenant data access = immediate security incident. Enforced at query layer, not just UI.
📁
File Storage
Tenant-scoped path: /uploads/{tenant_id}/{upload_id}/{filename}. Files served via /api/invoices/{id}/file with auth check — no direct storage URLs exposed to frontend.
🦠
Virus Scan
Every uploaded file scanned before storage (python-clamd or clamscan). Infected files rejected before any parsing or DB record creation.
🔑
ERP Credentials
Credentials loaded from vault at push time only. Never stored in DB. Never appear in logs. Scrubbed before any log statement (Rule 05 compliance).
📜
Audit Immutability
invoice_push_log and invoice_state_log: DELETE and UPDATE privileges revoked at PostgreSQL level. Append-only enforced at DB, not just application layer.

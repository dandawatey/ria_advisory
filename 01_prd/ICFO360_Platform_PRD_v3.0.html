Executive Summary
Problem

Finance teams across multi-entity organisations face three compounding problems that block strategic decision-making and create operational risk:

  • Latency — no group-level visibility between month-end cycles; CFO decisions made on 3–10 day old data
  • Manual consolidation — Excel-based roll-ups are error-prone, unauditable, and fail to scale with acquisitions
  • ERP fragmentation — when subsidiaries run different ERPs (BC, SAP, Odoo), a single consolidated view is impossible without a normalization layer

Business Context & Problem Statement
Current State — Any Multi-Entity Organisation

Each subsidiary or legal entity operates its own ERP instance with its own chart of accounts, dimension structure, fiscal calendar, and posting conventions. Consolidated reporting is produced through a manual process: subsidiary controllers export trial balances, email them to the group finance team, and a small team performs manual mapping, elimination, and aggregation in spreadsheets.

Pain PointDescriptionBusiness Impact
LatencyNo group-level performance visibility between period-end cyclesDecisions made on stale data; competitive disadvantage
ComparabilityNon-standard CoA, dimension taxonomies, customer master across entitiesCross-entity comparison unreliable; board reporting requires manual reconciliation
AuditabilityManual spreadsheet consolidation fails traceability requirementsRegulatory risk; inability to trace report line to source journal entry
ScalabilityAdding an acquired entity compounds manual effort linearlyDoes not scale with growth; M&A integration takes 6–12 months per entity
Analytics gapNo governed analytical store for BI, forecasting, or AI insightFinance team reactive, not predictive; AI initiatives blocked

Pillar 2 — Intelligent Data Lakehouse
Zone 1
Bronze
Raw, immutable Delta extracts partitioned by entity + ingest date. Full history preserved for replay and audit. WORM retention ≥ 7 years.

Typed, schema-enforced, SCD-2 history. Canonical CoA mapped. Deduped by natural key. Data quality rules gate promotion.

Gold
Conformed facts. IC-eliminated. FX-translated. DQ-gated. Consumption-optimised for dashboards, agents, and exports.
Pillar 3 — Agentic Processing (A2A) — See Section 10

Eight specialized AI agents communicate via the A2A (Agent-to-Agent) protocol. Each agent declares capabilities via an Agent Card manifest. The OrchestratorAgent routes tasks. Any agent can pause and ask Finance a targeted question rather than failing silently.

Pillar 4 — Unified Analytics

Role-aware dashboards for all five personas. Close cockpit for month-end management. Variance explorer for FP&A. InsightAgent for natural-language Q&A. CSV/Parquet export for external modelling.

Pillar 5 — Governed Security

RBAC via Entra ID or SAML IdP. Row-level security by legal entity. WORM audit logs. Column-level masking for PII. Compliance-ready for SEC 204-2, IFRS, local GAAP, GDPR.

Data Lakehouse & Harmonisation
Canonical CoA — 4-Level Standard
L1: Financial Statement  — P&L | Balance Sheet | Cash Flow
L2: Category             — Revenue | COGS | OpEx | EBITDA | Current Assets | ...
L3: Subcategory          — Salaries | Rent | Marketing | Cash | Receivables | ...
L4: Source Account       — ERP-native account code (drill-down only; read-only)

All reports query at L1/L2/L3. Every L4 account maps to exactly one canonical account. Mapping changes require two-person approval workflow with full history.

Agentic Layer — A2A Agent Mesh ★
🧠
Why Agentic? Static pipelines cannot handle real-world financial ambiguity: vendor names that don't match ERP masters, OCR failures on scanned invoices, multi-step IC reconciliation requiring contextual judgment, compliance interpretation across jurisdictions. AI agents reason, adapt, coordinate with each other, and ask Finance targeted questions — rather than failing with a generic error.
A2A Protocol — Core Concepts
ConceptDescription
Agent CardJSON manifest declaring name, capabilities[], inputSchema, outputSchema, endpoint_url, model. Published to Agent Registry on startup.
TaskUnit of work: task_id, context, messages[], artifacts[], state (submitted → working → completed / failed). Passed between agents via HTTP POST.
Agent RegistryCentral DB table dim_agent_registry. OrchestratorAgent queries it to find the agent capable of a requested capability.
OrchestratorAgentRouting hub. Receives user intent, looks up Agent Registry, creates Task, dispatches to capable agent, aggregates result.
HITLHuman-in-the-Loop. Any agent calls request_human_input(field, question, options[]) → pauses tool loop → Finance answers via UI → agent resumes.
A2A Communication Flow
User Intent → OrchestratorAgent
  → query dim_agent_registry for matching capability
  → create Task { task_id, context, capability }
  → POST to target agent's A2A endpoint
  → target agent runs tool loop:
      if ambiguous field:
        call request_human_input(field, question, options[])
        → pending_question stored in DB
        → agent PAUSES (returns PENDING token)
        → Finance answers via Review Console
        → POST /api/{resource}/{id}/answer
        → agent RESUMES with confirmed answer
  → agent returns Task result (state: completed / failed)
  → OrchestratorAgent aggregates → responds to user
  → every step logged in fact_agent_task (immutable append-only)

Security, Privacy & Compliance
Regulatory Framing

The platform is designed to support common financial regulatory requirements. Applicable obligations vary by jurisdiction and must be confirmed by the customer:

  • SEC Rule 204-2 (US RIAs) — books and records retention (7 years), immutability, accessibility
  • IFRS / local GAAP — audit trail from source journal entry to consolidated report
  • Reg S-P / GDPR — PII safeguarding, data residency controls, right to erasure (where applicable)
  • SOX-equivalent — segregation of duties, change controls, financial control environment
Security Controls
ControlImplementation
Encryption at restCustomer-managed keys (CMK); no platform-managed key exposure to data
Encryption in transitTLS 1.2+ on all API, DB, and storage connections
Network isolationNo inbound public access to storage or compute; Private Link / Private Endpoints
IdentitySingle IdP (Entra ID or SAML); no local accounts except emergency break-glass
Row-level securityEnforced at SQL/API layer; users query only entities their role grants access to
Column maskingPII fields masked except narrowly authorised roles; unmask requires elevated role + audit log
Immutable audit logsWORM storage; DELETE/UPDATE revoked at DB privilege level on audit tables
Secrets managementVault service (Azure Key Vault / AWS Secrets Manager / HashiCorp Vault); no credentials in code
Agent isolationEvery agent query includes tenant_id filter; cross-tenant data access = security incident
HITL auditEvery agent question + Finance answer logged in fact_agent_hitl_log (immutable)
Penetration testingAnnual third-party pen test; quarterly vulnerability scans; SAST + dependency scanning in CI
SOC 2Year 1: readiness assessment; Year 2: Type II target

  • Cloud platform subscription (Azure / AWS / GCP) with sufficient quota for lakehouse + compute

Glossary
TermDefinition
A2AAgent-to-Agent — Google's open protocol for AI agent communication via HTTP + JSON Task / Agent Card semantics. Each agent is an A2A-compatible HTTP server.
Agent CardJSON manifest declaring an agent's name, capabilities[], inputSchema, outputSchema, and endpoint URL. Published to Agent Registry on startup.
Bronze / Silver / GoldMedallion architecture zones: raw (Bronze) · conformed (Silver) · consumption-ready (Gold).
Canonical CoAStandard 4-level chart of accounts used across all entities regardless of native ERP CoA. Owned by group finance.
CDCChange Data Capture — propagating only changed rows since the last extract (incremental ingestion).
HITLHuman-in-the-Loop — an agent pauses its tool loop to ask Finance a targeted question; resumes when Finance answers via the UI.
ICIntercompany — transactions between legal entities within the same group; must be eliminated in consolidated reporting.
InvoiceAgentThe first live A2A agent (IC-27, Phase 1 GA): extracts invoice fields from PDF/Excel/Image, validates against 7 rules, and pushes to ERP with human review.
OrchestratorAgentThe routing hub of the A2A mesh: receives user intents, queries the Agent Registry, creates Tasks, dispatches to capable agents, aggregates results.
RPO / RTORecovery Point Objective / Recovery Time Objective — disaster recovery parameters.
SCD-2Slowly Changing Dimension Type 2 — preserves full history of dimensional attributes via effective-date rows.
Task (A2A)Unit of work in the A2A protocol: task_id, context, messages[], artifacts[], state (submitted → working → completed / failed).
WORMWrite Once Read Many — immutable storage policy required for regulated financial records.
ERPEnterprise Resource Planning — business management software (BC, SAP, Oracle ERP Cloud, D365F, JDE, Odoo, Tally).
